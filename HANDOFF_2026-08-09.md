## 3. Bugs found — fixed

**`MaterialOrder.code` was the string `"Enter code"`.** `RequestFlowForm.save()`
copied `unit` from the selected `InventoryItem` but never `code`, and the model
defaults to that placeholder. Material code is the BoQ join key, so **every
request raised through the single-request form could never reconcile against any
contract** — and before the gate existed it was released anyway. Only affected
single requests; bulk upload always set it correctly. Two production orders still
carry the placeholder: **13 (TILLI)** and **17 (KUKURANTUMI)**.

**jQuery was never loaded.** `base.html` loaded Bootstrap and nothing else, while
**14 templates** call `$(...)`. Symptom was a console `ReferenceError` and, on the
release-letter page, a request-code dropdown that silently ignored
`?request_code=`. Now loaded in `<head>`. **This is the riskiest change in the
session**: twelve of those templates have JavaScript that has never executed
once, and deploying switches it all on simultaneously. Walk them, or scope the
include, before shipping.

**The wizard path never versioned documents.** Releases were born at
`memo_version = 0` while `apply_signature` coerced a falsy version to 1 — so a
signature claimed v1 on a document the record called v0. Confirmed in live data
before the fix.

**`start.sh` omitted glib.** WeasyPrint dlopens `libgobject-2.0-0` by soname;
being installed as a Pango dependency is not the same as being loadable. Now
installs `libglib2.0-0t64` (falling back to `libglib2.0-0`) first and separately.
The answer was already written in `requirements.txt` two files away.

**Blank inventory codes.** `UploadInventoryView` accepted a NaN `code` cell, and
`get_or_create(code='')` then merges unrelated materials into one item — silently
combining stock balances. Now coerced and rejected with a message.

## 4. Bugs found — NOT fixed

**The Azure Startup Command does not run `start.sh`.** It is currently:

```
python manage.py migrate --noinput && gunicorn Inventory_management_system.wsgi
```

Migrations run; the WeasyPrint library install never has. **This is the single
blocker on all document generation in production.** Needs Site configuration
write permission — Leslie has read only. Request text is in §7.

**Bulk request upload cannot scale.** Each `mo.save()` fires four `post_save`
receivers; one creates notifications *and calls Microsoft Graph per
notification*. A 552-row upload is ~1,100 serialised outbound HTTP calls inside a
single transaction in a single request, which exceeds Azure's 230s ceiling and
500s. **Splitting into 94-row batches also failed**, so the ceiling is lower than
estimated and the cause is not fully confirmed — probe files
(`TEST_A_2rows`, `TEST_B_12rows`, `TEST_C_38rows`) were built to find it and had
not been run when the session ended. Real fix: skip or queue the email during
bulk import.

**Over-issuance justifications can be self-approved.** The model records
`reviewed_by` but does not constrain who may approve. The officer who raises one
can approve their own and clear the new generation gate. Marked `ponytail:` in
`reconciliation.py::_is_justified`; belongs in the review view. **The gate makes
this load-bearing — it matters more now than when it was found.**

**"Mark as released manually" has mismatched permissions.** The button renders
under `can_generate_documents` (Schedule Officers, Management, superuser) but
`MarkReleasedView.test_func` allows Store Officers, Stores Management,
Management, superuser. A Schedule Officer sees it and gets a 403; a Store
Officer, who is authorised, never sees it. Suggested fix: a `can_mark_released`
flag computed from the view's own test.

**`runtime.txt` is ignored.** It says `python-3.12.2`; the workflow pins `3.14`
and the container runs 3.14. Not the cause of any current failure — the
WeasyPrint traceback reaches `dlopen`, so the import chain is fine on 3.14 — but
a declared runtime nobody honours will bite eventually.

**64 Members of Parliament disappeared.** Prod had 64 before the 276-row import;
it has exactly 276 after. `upload_members_of_parliament` is a plain `bulk_create`
with no delete, so it did not do this. The old rows included a region spelled
`ASHANTI` (a case-duplicate) which is also gone. Worth establishing whether those
64 held emails, phones or districts that the new rows do not.

## 6. Files produced

`release_imports/` — communities, MPs and requests from the five letters.
`stock_imports/` — three store inventories, 181 items, codes mapped to the
Ministry's canonical list. Every row carries a `match` column:
**117 exact, 40 inferred, 24 NEW**. The inferred ones are mostly
polymer-vs-porcelain where the store sheets do not say. New codes follow the
prefix+number convention.

Two conflicts in the canonical list itself, worth fixing at source:
`BTC021` is against both *10Cu/120Al* and *16Cu/50Al*; `DT33/3PH004` is against
both *33/275KVA* and *33/50KVA*.

Stock files cannot upload until `Wa Area Store`, `Bolgatanga Area Store` and
`Sunyani Area Store` exist. **And note:** `InventoryItem` holds one quantity and
one warehouse per code, and the importer is additive (`quantity += `). Loading
all three stores sums them into a national figure and leaves the warehouse as
whichever uploaded last. Stay Wire would read 1,668,661.
