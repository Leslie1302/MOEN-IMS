# Implementation Plan — In-App Signing & Management Approval Queue

**Date:** 2026-08-06 · **Scope:** MOEN-IMS release documents (approval memo +
release letter) · **Goal:** management receives documents in-app, signs them by
drawing a signature, and can call the responsible officer for discussion — with
the existing wet-signature route preserved.

**Supersedes** decision 2 of `IMPLEMENTATION_PLAN_release_docs_2026-08-05.md`
("Signatures — deferred until the Chief Director is onboarded"). That deferral
ends here.

---

## 1. Decisions taken (do not relitigate)

| Question | Decision |
|---|---|
| Signature form | **Drawn in the browser** on a canvas at signing time, **plus a generated authority stamp**. No stored reusable signature asset. |
| Stamp content | Name, **office signed in**, **substantive designation**, timestamp, release code + version, verification token. |
| Wet signatures | **Both routes run.** Neither replaces the other. |
| MMU gate | **Advance notice on digital signature; physical release still on verified scan.** See §6. |
| Signing order | **Configurable ordered steps** per document type. More signatories will be added. |
| Change requests | **"Call officer for discussion"** button — Graph email + in-app notification. No formal reject state. |
| Versioning | **Version counter**; each dispatch records the version it sent. |
| Verification | **Public verify page** — token lookup, no login. |

**The chain in practice:** Ag. Director Power signs the *memo* (what he is
signatory to) → memo + letter then go to the Chief Director (or whoever is
acting) who signs the *letter*.

---

## 2. What exists today

- `Signatory` — config rows (name, title, `signs_for`, per-document default
  flags). **No user link, no signature image.** The PDF prints the name and
  title over a blank line.
- `Profile.signature_stamp` — a **text** token (CharField), auto-generated by a
  signal. Not an image. Useful as a verification code, not as a signature.
- `DocumentDispatch` (0081) — who emailed which documents to whom.
- Workflow: `draft → memo_generated → awaiting_signature → awaiting_scan_upload
  → approved → released`, plus `voided` / `reissued`.
- Documents render from HTML templates (`_doc_base.html`) via WeasyPrint, with
  `.sign-block` holding the name/title lines.

## 3. Approach

**Signatures are rendered, not stamped.** A captured signature becomes part of
the document *context* and is drawn into `.sign-block` by the existing template;
the PDF is then re-rendered. This avoids coordinate-hunting on a finished PDF,
survives letterhead and inset changes, and means the preview shows the signature
exactly as it will print — the property the whole rework is built on.

**Consequence that must be handled:** once signed, the document is frozen.
Re-generating a signed document would silently reproduce a signature over
changed content, which is forgery-adjacent. See §5.

---

## 4. Data model

### `SigningStep` (new)
Ordered approval chain, configurable in admin.

- `document_kind` — `memo` | `letter`
- `order` — 1, 2, 3…
- `signatory` FK → `Signatory`
- `user` FK → `User` *(who actually signs in-app; nullable so a Signatory can
  exist for print-only use)*
- `required` bool, `active` bool

`Signatory` gains `user` FK so a config row maps to a login.

### `DocumentSignature` (new)
One row per applied signature — the audit record.

- `release_letter` FK, `document_kind`, `step` FK → `SigningStep`
- `signed_by` FK → `User`, `signatory_name` / `signatory_title` *(denormalised —
  titles change; the record must say what was printed at the time)*
- `signature_image` — PNG of the drawn signature
- `signed_at`, `ip_address`, `user_agent`
- `document_version` — the version signed, so a signature can be tied to exact
  content
- `verification_token` — short code printed beside the signature

### `ReleaseLetter` additions
- `memo_version` / `letter_version` — increment on every Generate
- `memo_locked` / `letter_locked` — set when fully signed

### `DocumentDispatch` addition
- `memo_version` / `letter_version` sent — closes the audit hole where the
  history implies the *current* PDF was what went out.

## 4a. The authority stamp

`Profile.generate_signature_stamp()` today emits
`SIGNED_BY:{name}|TIMESTAMP:{iso}|ID:{uuid}` **once, at profile creation**. It is
a static per-user token: it exists before the user has signed anything and
proves nothing about a signing event. It is replaced by a **per-event** stamp.

What prints beneath the drawn signature:

```
─────────────────────────────
   [ drawn signature ]
─────────────────────────────
   KWAME MENSAH
   Ag. Chief Director                 <- office signed in (Signatory.title)
   (substantive: Director, Finance)   <- Profile.designation
   Signed 06 Aug 2026, 14:32 GMT
   MOEN-IMS · RE-2026-0001 · v3
   Verify: 7K2M-9QX4-A1B8
─────────────────────────────
```

**Why this carries the legal weight the scribble cannot.** It asserts who
signed, *in what office*, on what substantive authority, over which document at
which version, at what time — and offers a token any third party can check. The
scribble is the human mark; the stamp is the evidence.

**Why it also closes the image-reuse risk.** There is no stored reusable
signature file to lift. The drawing exists only as part of one signing event,
and a lifted scribble is inert because it carries no valid token. Verification
checks the stamp, not the picture.

### New fields
- `Profile.designation` — substantive post ("Director, Finance"). Distinct from
  `Signatory.title`, which is the office being signed in ("Ag. Chief Director").
  For an acting officer these differ, and the record must show both.
- `Profile.office` *(optional)* — directorate/unit.

## 4b. One reference: the registry adopts the IMS code

**Decided:** rather than carry a second, later-issued registry number, the
Registry adopts `RE-{year}-{NNNN}` as the official outgoing reference for release
letters. One number quoted by IMS, the Registry, MMU and Internal Audit.

This is better than the two-reference design it replaces because it removes the
gap entirely: the letter carries its official reference **from the moment it is
generated**, so there is never a window where MMU holds a document it cannot
formally cite. It also means the QR, the scan-match, the signature stamp and the
Registry file all key off the same string.

### What this obliges us to get right

Once this number is the Registry's, it is no longer a private internal
identifier and must behave like a registry sequence:

1. **Every issued number must resolve to a record — forever.** Including voided
   ones. A registry may tolerate gaps; it cannot tolerate a reference that
   resolves to nothing. Voided releases keep their number and show as
   `RE-2026-0042 — VOIDED`. The public verify page (Phase 6) is what makes this
   externally checkable, which is precisely what a registry needs.
2. **No duplicates, ever, under concurrency.** See §4c.
3. **Format is the Registry's call.** If they want `MOEN/IEPS/RE/2026/0001`, the
   allocator must render their convention. Make the format a setting rather than
   a literal, and agree it before the first letter is issued — the sequence
   cannot be reformatted retrospectively.
4. **Numbers are issued at generation, not at signing.** A generated-then-
   abandoned release consumes a number. Acceptable (see 1), but the Registry
   must be told to expect it.

## 4c. Blocker: the code allocator must be hardened first

`services/release_code.py` is not currently safe enough to back a registry
sequence. Two defects, both pre-existing:

**(a) It raises on PostgreSQL.** The allocator builds
`select_for_update().aggregate(Max('code'))`, which emits
`SELECT MAX(code) ... FOR UPDATE`. PostgreSQL rejects that outright:
*"FOR UPDATE is not allowed with aggregate functions."* Production is Postgres
(`DATABASE_URL` is the only supported production path; SQLite needs an explicit
emergency override), so this either errors today or is only working because the
box is still on the SQLite override.

**(b) Read-then-write race.** `next_release_code()` computes `max + 1` and
returns; the caller assigns and saves later. Two concurrent generations can read
the same maximum. Today the `unique=True` constraint on `code` turns that into
an `IntegrityError` — a failed generation rather than a duplicate, which is the
right failure — but it is still a user-visible error under load.

**Fix (Phase 0):** replace `Max()+1` with a dedicated single-row-per-year
`ReleaseCodeSequence` locked via `select_for_update()` on that row — race-free on
Postgres, correct on SQLite, no aggregate. Retry once on `IntegrityError` as a
belt-and-braces guard. Make the rendered format a setting.

**This must land before the Registry adopts the number.** A duplicate or failed
registry reference is a materially worse problem than a duplicate internal id.

## 5. Locking rule (the important one)

Once a document has any signature:

- **Generate is refused** for that document with a clear message.
- The WYSIWYG editor becomes read-only for it.
- To change it: **Void and reissue** — the existing `reissued` state — which
  discards signatures and starts a new version. Nothing silently re-signs.

Without this, an officer edits after the Director signs and the Director's
signature appears over wording he never saw.

## 6. Phases

### Phase 0 — Harden the code allocator (~0.5 day) — **do first**
`ReleaseCodeSequence` (one locked row per year) replacing `Max()+1`; configurable
rendered format; retry on `IntegrityError`; tests for concurrent allocation and
for Postgres. Blocks the Registry adopting the number (§4c).

### Phase 1 — Models + admin (~1 day)
`SigningStep`, `DocumentSignature`, version/lock fields, one migration. Admin
for the chain with inline ordering. Seed: memo → Ag. Director Power; letter →
Chief Director.

### Phase 2 — Signature capture + rendering (~1.5 days)
- Canvas signing modal: draw, clear, confirm. Pointer events (mouse/touch/pen),
  exports trimmed PNG.
- `_doc_base.html` `.sign-block` renders signature image + name + title +
  verification token + date when a signature exists; blank line when not.
- Re-render + re-mint the PDF on signing. Version increments; document locks
  when the chain completes.

### Phase 3 — Management approval queue (~1.5 days)
New page `/approvals/`:
- Documents awaiting **this user's** signature (their step is next and unsigned).
- Inline preview of the exact document, Sign / Call officer actions.
- Sections: awaiting me · awaiting others · recently signed by me.
- Gated to users named on an active `SigningStep`, plus Management.

### Phase 4 — Call officer for discussion (~0.5 day)
Button + note → Graph email from the manager's mailbox *and* an in-app
notification to the officer who prepared the release. Recorded against the
release so the conversation is on file. No workflow state change — a call for
discussion is not a rejection.

### Phase 5 — MMU fast-track: advance notice + management urgency (~1 day)

**Default route (every release).** On chain completion the release appears in
MMU's list immediately, marked **"Advance notice — prepare only, do not
release"**, quoting `RE-{year}-{NNNN}`. MMU picks and stages stock. Materials
leave only on the verified wet-signed scan. MMU stops waiting to *start*, which
is where most of the delay sits, and no control is waived.

**Urgent route (management directive).** A signatory-level **"Treat as urgent"**
action that clears MMU to release on the digital signature alone.

Guardrails — this is a directive, not a self-serve bypass:

- **Only users on an active `SigningStep`** may declare urgency. The officer
  raising the release cannot; the people who sign it can. That is the difference
  between a directive and a waiver, and it is the whole reason this is
  acceptable where a per-officer "urgent" checkbox would not be.
- **A reason is mandatory**, free text, recorded with who and when.
- **Visible everywhere** the release appears — list, detail, MMU view, and on
  the document itself.
- **Reportable**: an urgent-releases report, so Internal Audit can review the
  pattern rather than discovering it. If "urgent" becomes routine, that shows
  up as a number rather than as a finding.
- The wet-signed copy is **still required** afterwards; urgency changes *when*
  MMU may act, not *whether* the paper record exists. A release cleared urgently
  and never followed by a scan is flagged as outstanding.

`ponytail:` advance notice is a flag plus a filter on MMU's existing list — not
a new MMU screen.

### Phase 6 — Public verification page (~0.5 day)
`/verify/<token>/`, no login: release code, document, version, signer name,
office signed in, substantive designation, timestamp, and whether the document
was subsequently superseded. Rate-limited (`django-ratelimit` is already in the
stack); reveals nothing beyond what is printed on the document itself, and
**never the signature image**.

### Phase 7 — Verify (~0.5 day)
Signature and stamp render into the PDF; locking refuses regeneration; the chain
enforces order; advance notice never permits physical release; registry number
required before `approved`; version recorded on dispatch; the verify page
resolves a real token and rejects a forged one; queue shows only what a user may
sign.

**Estimate:** ~7 days, shippable per phase.

## 7. Risks — and how each is answered

- **Legal weight of a drawn signature.** *Resolved by design, not by assertion.*
  A scribble alone proves little; the **authority stamp** (§4a) carries office,
  substantive designation, document version, timestamp and a publicly checkable
  token. And the digital route never grants physical release on its own — the
  wet-signed, registered copy still governs (§4b, Phase 5). Nothing rests on the
  scribble being legally sufficient.

- **Signature image reuse.** *Resolved by drawing live.* No reusable signature
  file is ever stored, so there is nothing to lift. Per-event PNGs stay on
  access-controlled media, are served only inside the signed document, and never
  appear in a list view, an email body, or the public verify page.

- **Acting officers.** *Resolved by keeping the chain in data.* Three separable
  pieces: `SigningStep` (which office signs, in what order — changes rarely),
  `Signatory` (what name and title print — changes with the postholder), and
  `SigningStep.user` (whose login may sign — changes each acting appointment).
  An acting appointment is two field edits in admin, no deploy. The stamp shows
  the office signed in *and* the substantive designation, so the record never
  leaves ambiguous who acted under what authority.

- **Urgency becoming the default.** The real risk of the urgent route is not a
  single misuse but quiet normalisation. Answered by restricting it to
  signatories, requiring a recorded reason, showing it everywhere the release
  appears, and reporting on it — so a drift toward routine urgency surfaces as a
  trend Internal Audit can see, rather than as a finding after the fact.

- **A registry sequence with holes or duplicates.** Answered by Phase 0 (§4c)
  and by retaining voided numbers as resolvable records.

## 8. Dependencies on the Ministry

1. **Registry adopts `RE-{year}-{NNNN}`** as the official outgoing reference for
   release letters — and confirms the **format** before the first letter is
   issued, since the sequence cannot be reformatted retrospectively.
2. **Registry accepts that numbers are issued at generation**, so an abandoned
   release consumes one.
3. **MMU accepts the advance notice** as authority to pick and stage (not to
   release). If not, Phase 5's default route reduces to visibility only; the
   urgent route and everything else stand.
